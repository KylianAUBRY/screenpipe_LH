# AGENTS.md

screenpipe captures accessibility trees (OCR as fallback) and conversations, and
indexes them locally for AI consumption. It is the context layer for agents.

This file is loaded into every agent's context. Keep it short; put detail behind
a pointer.

## Hackathon mode (temporary)

This fork is used for a 2-day hackathon: add a **more deterministic and
reviewable automation system than pipes**, called an **Automation Flow** (or
**Flow**). A Flow is backed by an n8n workflow: an AI creates the workflow and
the review material, the user reviews it, and activation runs it.

**Product direction**: when ScreenPipe detects a repetitive task, it notifies
the user. The notification opens the **task page** of that detected task (not
the Flow): what was detected, a button to show the evidence timeline, and
**mandatory clarification questions** written by the AI. Once every question is
answered, the AI creates the Flow from the task and the answers, then the user
lands on the Flow review screen. In the finished product, detected tasks come
from the `workflow-*` detection pipeline. Flows are normally generated by an AI
from the detected task or from a chat request. The review screen includes a
plain-language summary of what the Flow does and how, and a visual reproduction
of the n8n graph (rendered from the workflow structure, not a screenshot) with
one short AI-written sentence per node, plus the review actions described
below.

**Demo contract**: the notification, the detected task and its clarification
questions are scripted, and the n8n workflow is pre-built; no detection runs
for the demo. The evidence timeline comes from a real recorded session (a few
real repetitions). Flow creation after the questions is scripted: the answers
are saved but do not change the result; the pre-built workflow and its
pre-written review material are imported into n8n inactive as is, so the user
can open and edit it there; activation only switches it on. Activation and the
Gmail→Jira execution are real. For the demo, no detection-side wiring is in
scope.

**Terminology**: an **Automation Flow** is our automation type, backed by an
n8n workflow — distinct from ScreenPipe's existing automations and pipes.

- **Reference case**: creating Jira tickets from bug-report emails (support).
  It is the only scenario the demo covers; everything else is post-hackathon
  parking.
- **Detection is already implemented in ScreenPipe — do not rebuild it.**
  Adapt it only if needed. In the finished product, proposals come from the
  `workflow-*` detection pipeline; the demo proposal is scripted. Detection
  reads ScreenPipe's captured activity, not the Gmail inbox; Gmail is only the
  n8n trigger.
- **An Automation Flow is backed by an n8n workflow, not a ScreenPipe
  pipe.** n8n is self-hosted locally and is the source of truth for workflow
  content and state; read that state from n8n rather than keeping a separate
  copy in the app. Workflows — trigger included — live in n8n and are edited
  there. For the reference case, the workflow starts with an email trigger (in
  n8n) and ends with Jira issue creation; it includes an AI step that decides
  whether an email warrants a ticket, and other middle steps are free — use
  them to make n8n's value visible.
- **ScreenPipe n8n nodes (hackathon scope)**: build two custom n8n nodes.
  (a) **ScreenPipe Trigger (AI)**: takes a condition prompt and continuously
  evaluates it with AI; when the condition is met, it triggers the workflow.
  (b) **ScreenPipe Trigger (deterministic)**: triggers on a keyword detected in
  the transcription, a specific window becoming active, or another Flow/pipe
  firing. These nodes are what make the automation layer more capable than
  pipes.
- **Keep AI minimal**: use AI only where judgment is needed; everything else
  is deterministic.
- **An Automation Flow can be created from the ScreenPipe chat.** Chat-created
  Automation Flows still go through the review screen and explicit activation.
- **Task page direction**: reuse ScreenPipe's existing detected-workflow page
  (`packages/workflows-ui`, opened by the existing `screenpipe://workflows`
  notification deeplink); it shows the detected task, the evidence timeline
  with real screen captures and a "View in timeline" link, and the
  clarification questions; questions are mandatory only for creating a Flow;
  answering all of them enables the action that creates the Flow.
- **Review screen direction**: lives in the existing Automations tab, opened
  once the Flow is created from the task page; plain-language explanation; a
  link back to the task page and its evidence; a read-only visual reproduction of the
  n8n workflow with one short AI-written sentence per node; a "View graph" link
  that opens the workflow in n8n for advanced users — editing happens there; do
  not reimplement the n8n editor in the app; a "View in timeline" link that
  shows where the task was detected; a chat to request changes that updates the
  workflow and its review material — editing an active Flow pauses it, creates
  an inactive version, and requires re-review before re-activation;
  activate/deactivate; no separate trigger section (the trigger lives in n8n);
  nothing activates without an explicit user action (activation through the app
  goes via the n8n API).
- **Automation Flows view**: lives in the existing Automations tab; lists the
  Automation Flows created from the app (tagged in n8n), with an Add button
  that opens a creation chat; selecting a Flow opens a detail view with more
  information, basic stats (status, last run), and activation history.
- **Real integrations**: Gmail (dedicated account, IMAP + app password) and
  Jira (Cloud, email + API token) are real integrations, configured in n8n —
  not through ScreenPipe's Connections.
- **AI model**: the user's ChatGPT subscription, everywhere. The ScreenPipe
  chat (Flow creation included) uses the ChatGPT preset (Settings → AI →
  ChatGPT). AI nodes in n8n workflows and the ScreenPipe AI Trigger name a
  `chatgpt/<model>[:<effort>]` model on the local OpenAI-compatible proxy
  (`:3030/v1/chat/completions`), which answers with the ChatGPT sign-in the
  app holds; `auto` on the same proxy still reaches the ScreenPipe
  subscription. Model everywhere: `gpt-5.6-luna` at `max` reasoning effort
  (`chatgpt/gpt-5.6-luna:max`; the chat's Effort slider on Max).
- **Situational triggers are generic**: any PC situation ScreenPipe can
  observe can trigger an n8n workflow (not just the reference case); this is
  implemented by the two ScreenPipe trigger nodes above.

## Source file header

For source code files in this repository, add this header at the top, below any
shebang or `use` line that must come first. Use `//` for Rust/TS/JS/Swift and
`#` for Python:

```
// screenpipe — AI that knows everything you've seen, said, or heard
// https://screenpipe.com
```

Do not add the header outside this repository. Agent-facing prompt and
instruction artifacts—including `AGENTS.md`, `CLAUDE.md`, `SKILL.md`, prompt
fixtures, and generated copies of those artifacts—are exempt because their
contents can be interpreted as instructions by downstream agents.

## Tooling

`bun` for JS/TS, never npm or pnpm. `cargo` for Rust. Check CI after pushing.

Scope test runs; the workspace is ~490k lines. `cargo test -p <crate>`, or
`cargo test --workspace --exclude screenpipe-rfdetr-mlx` as CI does. Frontend is
`cd apps/screenpipe-app-tauri && bun run test`.

`src-tauri` is excluded from the workspace and has no CI test job, so root
`cargo test` never compiles it. From `apps/screenpipe-app-tauri`, test it with
`bun run test:tauri <cargo-test-args>`. This command runs `pre_build.js`, uses
the `debug-dev` profile, and holds the machine-wide native build queue for the
entire test. It can rewrite tracked `src-tauri/gen/schemas/`; restore only that
generated noise afterward.

For native app development, use only the scripts in
`apps/screenpipe-app-tauri`: `bun run dev:tauri` for the normal live loop,
`bun run build:tauri:dev` for a one-shot test binary, and `bun run test:tauri`
for native tests. They select the `debug-dev` Cargo profile and use the
machine-wide native build queue/cache automatically. Never run raw
Tauri/Cargo commands for `src-tauri`, even for one focused test. If the queue
or sccache is unavailable, stop and report the native check as blocked; never
accept or continue a local-compilation fallback. Do not use `cargo clean`,
target-directory overrides, or ad hoc profile/cache settings.
See `docs/macos-dev-builds.md` for the exact commands and for the separate
signed `.app` path used only when persistent macOS TCC identity is required.

## Hot paths

Recording is the critical path. Never sacrifice an authorized recording to
archival, compression, indexing, redaction backlog, sync, or other background
work. Persist captures durably through the existing writer; processing budgets
bound background work, never capture admission. When processing cannot keep up,
retain the recording and defer that work. Preserve privacy, user pause controls,
and genuine disk/data-integrity protections. Tests must prove continued durable
recording and recovery under processing failure, backlog, and restart; replace
expectations that require recordings to be rejected or dropped for those reasons.

Capture and encode per frame (`screenpipe-screen`, `-capture`, `-a11y`), audio
device callbacks (`screenpipe-audio`), and SQLite writes (`screenpipe-db` via
`-sqlite-coordinator`) run continuously on every user's machine. No per-frame
allocation, no blocking a callback, no second DB writer. A regression there is a
battery or data-loss bug; say so in the PR and measure it. Each crate's `//!`
header has the specifics.

## Testing

Test your work at the narrowest boundary that proves it — review is the
bottleneck. For ordinary desktop React/layout changes, use the browser-mock loop
documented in `apps/screenpipe-app-tauri/README.md`; do not build Tauri merely
for UI validation. Drive the real app only when the change crosses a native
boundary listed there. Put before/after visuals in every issue and PR body:
screen recording, screenshots, HTML mockup screenshot, or ASCII.

Before opening or updating a PR, run every eval relevant to the changed behavior
locally and put the exact commands and results in the PR body. CI is a second
signal, not a substitute.

## Publication boundary

Agents may bump versions, push source, build, sign, notarize, and upload
versioned artifacts. Agents must never publish: no writes to `latest.json`,
`beta/latest.json`, or `enterprise/published.json`; no `app-v*` / `app-beta-v*`
tags or GitHub releases; no `app-publication` approvals; no calls to the admin
publication endpoint; and never weaken the `Human-only app publication tags`
ruleset. Publication is a human click in the admin releases UI.
